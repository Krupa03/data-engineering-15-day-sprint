# Day 15 - Final Project: E-Commerce Data Platform

## 1. Problem Statement
This platform solves the problem of scattered and disconnected data across an online store. Specifically, it answers:
- Which marketing ads are driving actual purchases vs. wasting money on empty clicks?
- Which loyal customers haven't bought in 30 days so we can offer them a discount before they leave permanently?

## 2. Architecture
Our data platform works like a giant digital plumbing system. Live info about clicks, purchases, and stock is automatically collected from the website and payment systems. This messy, scattered data flows through secure digital pipes into one central storage warehouse where it is cleaned and organized. Fresh, neat data then flows to live dashboards showing business owners exactly how the store is performing at any given second.

## 3. Technologies Used
- **Airflow** – orchestration, scheduling, and retry logic
- **dbt** – SQL transformations and data quality tests
- **Kafka** – real-time ingestion of user clicks and order events
- **Snowflake** – central cloud data warehousing for scalable storage and compute
- **PostgreSQL** – reliable transactional database for primary store data
- **Tableau** – business intelligence dashboards for real-time reporting
- **PySpark** – large-scale data transformations and streaming processing
- **Databricks** – unified lakehouse platform for Spark workloads and Delta Lake
- **Delta Lake** – ACID-compliant storage layer with time travel and schema enforcement
- **Terraform** – infrastructure as code for provisioning cloud resources
- **GitHub Actions** – CI/CD pipeline for automated testing and deployment
- **Docker** – containerization for consistent environments
- **BigQuery** – cloud data warehouse for analytical queries on large datasets

## 4. Batch Pipeline
- **Step 1: Extraction** – Fivetran pulls raw data from PostgreSQL every night
- **Step 2: Landing** – Raw data lands in Delta Lake Bronze layer on Databricks
- **Step 3: Processing** – PySpark jobs clean and transform data at scale
- **Step 4: Warehousing** – Cleaned data moves into BigQuery and Snowflake
- **Step 5: Modeling** – dbt transforms raw data into business-ready tables
- **Step 6: Quality Check** – dbt runs not_null, unique, and relationship tests
- **Step 7: Reporting** – Tableau dashboards refresh with new data
- **Control Center** – Airflow schedules and monitors every step

## 5. Streaming Pipeline
- **Step 1: Generation** – user clicks, add-to-cart, and payment events generated by website
- **Step 2: Ingestion** – Kafka captures every event into dedicated topics partitioned by user_id
- **Step 3: Processing** – Spark Structured Streaming cleans events and applies watermarking for late data
- **Step 4: Storage** – processed events written to Delta Lake Bronze → Silver → Gold via Medallion architecture
- **Step 5: Consumption** – Gold layer feeds live Grafana dashboards showing orders/minute and revenue

## 6. Data Model
**Fact Table:**
- fact_orders: order_id, user_id, product_id, timestamp, quantity, total_amount

**Dimension Tables:**
- dim_users: user_id, user_name, country, signup_date
- dim_products: product_id, product_name, category, price
- dim_time: timestamp, minute, hour, day

## 7. Data Quality
- **Schema Enforcement** – Delta Lake rejects incoming data that doesn't match the expected schema
- **dbt Tests** – not_null, unique, and referential integrity tests run after every transformation
- **Deduplication** – ROW_NUMBER() window functions keep only the latest record per order_id
- **Watermarking** – Spark handles late-arriving events within correct time windows
- **Medallion Filtering** – Silver layer filters null order_ids, negative amounts, and invalid user_ids

## 8. Error Handling
- **Automated Retries** – Airflow retries failed tasks up to 3 times with a 5-minute cooldown
- **Dead Letter Queue** – Kafka routes malformed messages to DLQ topic so bad records don't block pipeline
- **Checkpoints** – Spark resumes exactly where it stopped after any crash
- **Alerting** – email alerts fire on task failure with exact error logs

## 9. Incremental Processing
- **Spark Structured Streaming** – processes only new events since last micro-batch
- **Auto Loader** – tracks ingested files using file notifications, picks up only new files
- **Watermarking** – captures late events within the correct window without full reprocessing
- **Checkpoints** – store exact Kafka offset so pipelines resume without data loss

## 10. Monitoring
- **Grafana Dashboards** – real-time panels for orders/minute, revenue, and pipeline latency
- **Consumer Lag Tracking** – Kafka lag monitored to detect streaming pipeline falling behind
- **Health Checks** – Airflow DAG history shows success/failure rates with SLA miss alerts
- **Alert Notifications** – alerts fire when consumer lag exceeds threshold or dbt tests fail

## 11. Why Databricks?
Databricks is the native platform for Apache Spark, eliminating complex cluster management. Delta Lake is built in, giving ACID transactions, time travel, and schema enforcement out of the box. Auto Loader handles incremental file ingestion automatically. The unified workspace combines notebooks, jobs, and data lineage in one place, reducing tool sprawl.

## 12. Why Snowflake?
Snowflake's separation of storage and compute allows multiple teams to run heavy queries simultaneously without resource contention. Virtual warehouses auto-suspend when idle, making it cost-efficient. Micro-partition pruning delivers fast performance without manual indexing. Standard SQL means analysts can query data directly without learning a new language.

## 13. Why BigQuery?
BigQuery's serverless architecture means no infrastructure to manage and automatic scaling for any query volume. Columnar storage delivers fast performance on billions of rows. Native integration with GCS, Looker Studio, and Vertex AI makes it natural for GCP-based pipelines. Built-in ML allows model training directly on warehouse data.

## 14. Why Airflow?
Workflows defined as Python code are version-controlled, testable, and reproducible. Dependency management ensures correct task order and blocks downstream tasks on failure. The rich plugin ecosystem provides pre-built operators for every major cloud service. Robust retry logic makes the pipeline self-healing for transient failures.

## 15. Why dbt?
dbt brings software engineering best practices to SQL — version control, testing, and documentation in one tool. SQL-based transformations mean the entire analytics team can contribute without learning Python. Built-in testing catches data quality issues before bad data reaches dashboards. Automated lineage graphs show exactly how every table is built and which sources it depends on.
